# Cloud Courier reflection — review before submission

1. **Setup and payload.** This project uses my existing `inclass12-ee8cb` Firebase project and an Android emulator with Google Play services. Firebase initializes before Messaging, using Core 4.x and Messaging 16.x. String data `action=update_ui` selects either `asset=default` or `asset=promo` through a fixed allowlist of bundled PNGs and titles. Payload text never becomes an unchecked file path. Notification permission was authorized, and the UI displayed only masked token information.

2. **Lifecycle and evidence.** T1 shows foreground `onMessage` with the promo UI. T2 shows `onMessageOpenedApp` after tapping a background notification. The first T3 attempt still had a running process and returned the background callback. After a successful recents dismissal, an independent process check found no process; T3 then showed `getInitialMessage` and count one following a notification tap. The corresponding T1, T2, and T3 screenshots document these observations. Separately registered `onBackgroundMessage` performs background-safe work without widget state or a foreground context, so it cannot directly rebuild the visible UI.

3. **Validation and improvement.** T4 shows `asset=unknown` rejected while the promo title/image remained unchanged and the count increased from one to two. The T3 retry demonstrated why process state must be checked rather than inferred from a swipe. A feasible improvement is automated service-disposal testing with an injected messaging adapter: passing tests should prove pending initialization cannot notify disposed listeners. Codex assisted implementation, testing, evidence capture, and drafting; the course-specific disclosure rule still needs verification.
